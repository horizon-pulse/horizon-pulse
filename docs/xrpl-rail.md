# XRPL RLUSD rail (feature flag, OFF)

Branch `xrpl-rlusd-flag`. This is code only. **It is off in production and on every deploy unless someone sets the env vars below.** No wallet, account, key or facilitator sign-up was created to build it.

## What the flag does

When it's on, every paid route's 402 (the `PAYMENT-REQUIRED` header, plus the JSON body where the body is a PaymentRequired) and its OPTIONS response get **one extra `accepts` entry appended after the Base USDC entry**. That entry is an x402 `exact` payment in **RLUSD on the XRP Ledger**, at the same USD price. Base stays first and unchanged.

| route price | Base entry (unchanged) | XRPL entry |
|---|---|---|
| $0.005 | `amount: "5000"` USDC (6 dec) | `amount: "0.005"` RLUSD |
| $0.015 | `"15000"` | `"0.015"` |
| $0.04 | `"40000"` | `"0.04"` |

The XRPL entry follows `specs/schemes/exact/scheme_exact_xrpl.md` and `@x402/xrpl@2.27.0`:

```json
{
  "scheme": "exact",
  "network": "xrpl:1",
  "amount": "0.005",
  "asset": "524C555344000000000000000000000000000000",
  "payTo": "<HP_XRPL_PAYTO>",
  "maxTimeoutSeconds": 300,
  "extra": { "issuer": "<RLUSD issuer for the network>", "areFeesSponsored": false }
}
```

- `network` is CAIP-2: `xrpl:0` is mainnet and `xrpl:1` is testnet.
- `asset` is the RLUSD 160-bit currency hex, and `extra.issuer` is Ripple's issuer. Mainnet uses `rMxCKbEDwqr76QuheSUMdEGf4B9xJ8m5De`, pinned in `lib/xrpl-config.ts` and cross-checked against the package at init. Testnet uses the package's `RLUSD_TESTNET_ISSUER`.
- `amount` is the IOU **decimal value string**. The spec defines no `decimals` for XRPL IOUs and says implementations MUST NOT derive amounts from one. We convert from each route's USDC atomic price with integer string math, so there are no floats.
- `areFeesSponsored: false` is required by the spec. The payer always pays the XRPL fee.
- We never emit t54's `extra.sourceTag`, and we never use Memos.

No discovery copy changes in either mode: llms.txt, openapi.json, /.well-known/x402, skill.md, /agents, the browser 402 page and Bazaar metadata all stay as they are. Any public XRPL copy is class A and needs Odin's sign-off first.

## Env vars

| var | required | default | notes |
|---|---|---|---|
| `HP_XRPL_ENABLED` | yes | unset (off) | On **only** when it is exactly `true`. `TRUE`, `1`, ` true` and similar all mean off. |
| `HP_XRPL_PAYTO` | yes | none | XRPL **classic** address (`r…`), checksum-verified. If it's missing or invalid, the rail is off. It may not be the RLUSD issuer. |
| `HP_XRPL_NETWORK` | no | `xrpl:1` (testnet) | `xrpl:0`/`mainnet` or `xrpl:1`/`testnet`. Anything else means off. |
| `HP_XRPL_FACILITATOR_URL` | mainnet: yes | testnet: `https://x402.org/facilitator` | https only. Mainnet has **no default**: it must be named explicitly, otherwise the rail is off. No facilitator is hardcoded for mainnet, t54 included. |
| `HP_XRPL_ASSET_TRANSFER_METHOD` | no | unset (clients use `sequence`) | `sequence` or `ticketSequence`. See "Open questions". |
| `HP_XRPL_INIT_TIMEOUT_MS` | no | `2500` | Maximum wait for the XRPL facilitator's `/supported` on a cold instance. |

## Isolation (Base can't be affected)

- `lib/xrpl-config.ts` is pure, synchronous env parsing with no XRPL package import, and it never throws.
- `lib/xrpl-rail.ts` loads `@x402/xrpl` with a **dynamic import, only when the flag is on**.
- XRPL has its **own** `x402ResourceServer`, and its **only** facilitator is the XRPL one. That facilitator is wrapped so it advertises, verifies and settles nothing but the configured `xrpl:N`. The Base server keeps CDP as its only facilitator, exactly as before. A Base payload can only reach CDP and an XRPL payload can only reach the XRPL facilitator, even through `@x402/core`'s fall-back-to-any-client path.
- How requests are routed:
  - **Unpaid:** the Base 402 is built exactly as on main, then the RLUSD entry is appended. If anything fails (package import, scheme init, facilitator down or slow, facilitator not listing `xrpl:N`, header parse), the untouched Base 402 is served and `[xrpl-rail] …` is logged. A failed init is cached for 60s.
  - **Paid, payload's `accepted.network` is `xrpl:*` and the flag is on:** the request goes to the XRPL-only handler, after a static spec preflight. If the rail is unavailable, the preflight rejects, or anything throws, the Base-only 402 is served. That 402 is built from a copy of the request with the payment header stripped.
  - **Every other paid request (all Base payments):** the unchanged main code path.
- The hosted `/mcp` server stays Base-only for now.

## Tests (`npm test`, vitest)

- `tests/x402-flag-off.test.ts`: byte-identity against `tests/fixtures/x402-flag-off.golden.json`. The golden was generated by running the same harness on a clean `origin/main` (fc7e5f6) checkout before any XRPL code existed. It covers all 13 routes × (GET JSON, GET browser, POST for http/extract, OPTIONS) × (CDP mode, local mode), plus /.well-known/x402, /skill.md and the hashes of openapi.json, llms.txt and x402list.txt, across 9 flag-off env variants.
- `tests/xrpl-flag-on.test.ts`: Base first and byte-identical, then RLUSD second, with the correct network, asset, issuer, amount and payTo on every route, method and mode. Also covers mainnet and ticketSequence variants.
- `tests/xrpl-wire-format.test.ts`: builds spec-shaped payloads (unsigned XRPL Payment blobs, no keys) and checks that spec deviations are rejected: Memos (t54-style), Paths, partial payment, SendMax rules, NetworkID, wrong issuer/value/destination, and envelope mismatches.
- `tests/xrpl-isolation.test.ts`: import failure, scheme failure, facilitator down/hanging/not listing xrpl, and XRPL verify or settle throwing. In every case the result is the main-identical Base 402, a Base payment still settles via CDP only, and XRPL payloads only ever reach the XRPL facilitator.
- `tests/xrpl-config.test.ts`: flag parsing, r-address validation (cross-checked against xrpl.js), price conversion for all 13 prices, and the issuer constant matching the package.

Test addresses are derived from fixed filler bytes. They aren't wallets, and no key exists for them.

## Open questions / spec ambiguities

- **Long-running routes and `sequence`.** The spec says resource servers with long-running handlers SHOULD require `ticketSequence`. With `sequence`, a payer that uses its sequence between verify and settle invalidates the payment after our handler has run (free delivery). That affects fetch, extract, screenshot, search and pdf. `ticketSequence` adds buyer friction (a ticket reserve of 0.2 XRP each). The default here is unset, meaning the client defaults to `sequence`. This is a policy call for Odin and Michael. The env var allows `ticketSequence` globally, but not per route yet.
- **t54 interop.** t54 lists `extra.sourceTag` as required and allows Memos binding. The Foundation spec defines no `sourceTag` and forbids Memos. We follow the spec: we never emit `sourceTag`, we tolerate it in a payer's `accepted.extra` and as a tx `SourceTag` (the spec is silent), and we reject Memos. Whether t54's facilitator accepts spec-shaped requirements is unproven until testnet.
- **x402.org facilitator** is for testnet only. Its `/supported` listed `xrpl:1` when checked live on 10/8. It is not a mainnet default.
- **Settle-failure 402.** When an XRPL payment fails verify or settle, `@x402/next` returns its 402 from the XRPL-only server, so that error 402 lists only the RLUSD entry. The unpaid 402 always lists both.
- **Bazaar.** XRPL settles don't index or refresh CDP Bazaar. Base settles still matter. Whether a second, non-CDP `accepts` entry changes Bazaar's stored record is unknown: try one route first.
